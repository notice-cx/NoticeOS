# A site's uptime, checked by the OS itself (bead `ro-ujb9.165`)

**Decision (operator, 2026-09-23):** the OS checks each site's domain itself on
a schedule. No account and no connect step. A site's Data sources row shows
**Up** or **Down** with when it was last checked; a site that is down is an
error alert through the existing flag rules.

## What already existed, and was reused

The nightly served-layer sweep (`workers/ingest/src/hygiene.ts`, docs/08 §S5)
already GETs every site's home page at 04:00 UTC — `https://<domain>/`, the
OS's honest User-Agent, a 15-second ceiling — stores the reading in
`hygiene_checks` (check `html-depth`: `ok` / `warn` / `error` / `unreachable`,
the HTTP status, `observed_at`) and files `hygiene-home-unreachable` when the
page does not answer (the "Home page check failed — HTTP 404" alerts). Its
egress gate (`workers/ingest/src/egress.ts`) already refuses to accuse a site
when the OS's own network is down.

So uptime is that check, run more often and named:

| Piece | Where |
|---|---|
| The check, hourly | `runUptimeChecks` in `workers/ingest/src/hygiene.ts`, a second step (`uptime`) on the existing hourly tick (`FRESHNESS_CRON`, `workers/ingest/src/dispatch.ts`). A site read within the last 30 minutes is skipped, so the 04:00 sweep and the 04:00 tick are one request. |
| The reading | the existing `hygiene_checks` row, one a site a day; the hour's check replaces the day's reading. No new table, no new column, no migration. |
| Down → alert | the existing `hygiene-home-unreachable` rule, now filed at **error** (it was `warn`); an open `warn` flag is raised by the next check that still finds the site down, and the first check it answers retracts it. Since bead `ro-ujb9.180` only a failure a second GET confirms files it — see [Confirming a failure](#confirming-a-failure-bead-ro-ujb9180). |
| The row | the register cell for `uptime` reads the newest reading (`uptimeState`, `apps/tower/worker/integration-evidence.ts`): answered → Up (working, aged against a 1-hour cadence, so a check that stops running reads Not checked); did not answer → Down with the HTTP status or "No response"; OS offline → Not checked. A site with no reading yet shows no row (bead `ro-ujb9.133`'s rule). |
| The words | `connectionLabel(kind, auth, lane)` in `apps/tower/shared/connection-status.ts`: the uptime source reads Up / Down wherever a source's status is drawn — its Data sources row, the site header's source marks, the Health grid. |

## Prior art

Research 2026-09-23. The vendors' docs define state words, cadence and down
confirmation; none documents the exact list-row layout.

| Product | Source | What it does | Adopted |
|---|---|---|---|
| Better Stack | https://betterstack.com/docs/uptime/api/get-a-single-monitor/ | Monitor states `up`, `down`, `pending` ("waiting for the first check"), `paused`, `maintenance`, `validating`; the API carries `last_checked_at`. | **Up / Down** as the state words; the last-check time as the row's one fact. |
| Better Stack | https://betterstack.com/docs/uptime/check-frequency/ | 3 minutes on the free plan, 30 seconds paid. | Hourly here (the existing tick); the age beside the word says how fresh it is. |
| Better Stack | https://betterstack.com/docs/uptime/locations-and-regions/ , https://betterstack.com/docs/uptime/confirmation-and-recovery-period/ | Checks from at least four locations; an incident needs three failing; a confirmation period before an incident, a recovery period after. | With one checker, the egress gate is the confirmation: a fetch with no answer asks whether the OS can reach the network at all before accusing the site. |
| UptimeRobot | https://uptimerobot.com/api/legacy/ | States: paused, not checked yet, up, seems down, down. | "Not checked" for a site the OS could not check (offline, or a check that stopped). |
| UptimeRobot | https://help.uptimerobot.com/en/articles/11358448-uptimerobot-monitor-not-working-troubleshooting-guide | A new monitor is grey "preparing" until its first check, about 10 seconds after creation. | A new site shows no uptime row until its first check (within the hour). |
| UptimeRobot | https://help.uptimerobot.com/en/articles/11360876 , https://help.uptimerobot.com/en/articles/11358522 | Free plan checks every 5 minutes; up to three re-checks from one region before down. | Not adopted: hourly, and one check; see Better Stack row for confirmation. |
| Vercel (Geist) | https://vercel.com/geist/status-dot | Status dot with a word beside it ("color is not the only signal"); do not reuse the deployment dot for other kinds of status; use a gauge for health summaries that need a number (uptime %). | Word + glyph chip (the registry's `IntegrationStateChip`), never colour alone; no uptime % or history bar in the row. |
| Vercel | https://vercel.com/kb/guide/monitor-uptime-for-ai-native-apps-with-vercel-alerts | No scheduled pings of its own; alerts watch real traffic. | — (confirms a platform may not check uptime; the OS does). |
| Pingdom | https://documentation.solarwinds.com/en/success_center/pingdom/content/topics/why-does-pingdom-say-my-site-is-down-when-it-is-not-.htm | "Unconfirmed down" from one location, "down" only after a second location agrees. | Same idea as the egress gate: never accuse on a failure that may be the checker's. |

**Pattern adopted:** one state word with a glyph (Up · Down · Not checked), and
"checked 12m ago" beside it; a Down row adds what the page answered
("HTTP 503 · checked 12m ago"). No uptime percentage and no history bar: an
hourly check gives too few readings for either to mean much.

## Confirming a failure (bead `ro-ujb9.180`)

**Problem (2026-09-24):** one failed GET filed the `error` alert. A transient
5xx, a slow origin, a deploy in progress or a CDN hiccup put a red "1 source
failing" on the Wall, a red row in Needs you, and an alert the next hour
closed. False alarms are the fastest way to make the operator stop reading
the Wall.

**What every uptime product does:** confirm before alerting.

| Product | Source | What it does |
|---|---|---|
| UptimeRobot | https://help.uptimerobot.com/en/articles/11358522 | "A single failed check does not immediately mark a monitor as Down": up to three re-checks in the same region, 10–20 seconds apart. |
| Pingdom | https://documentation.solarwinds.com/en/success_center/pingdom/content/topics/why-does-pingdom-say-my-site-is-down-when-it-is-not-.htm | A first failure is "Unconfirmed Down"; the check "will only be marked as confirmed Down if the second test fails", from another probe server. |
| Better Stack | https://betterstack.com/docs/uptime/confirmation-and-recovery-period/ | A confirmation period — "how long we wait after observing a failure before we start a new incident" — and checks from several regions before an incident opens. |

**Adopted:** one retry, 45 seconds later (`HOME_CONFIRM_WAIT_MS`), inside the
same run. With one checker there is no second location, so a second look in
time is the confirmation, as UptimeRobot does within one region.

| Case | Reading | Alert | Row |
|---|---|---|---|
| First GET answers | `ok`, as before | retracts an open one | Up · checked 12m ago |
| First fails, retry answers | `ok`, with `failed_tries: 1` and the first try's status | nothing filed; retracts an open one | Up · checked 12m ago · 1 failed try |
| Both fail | `error` / `unreachable`, with `failed_tries: 2` | `hygiene-home-unreachable` at error, or the open one refreshed | Down · HTTP 503 · checked 12m ago |
| No answer and the OS is offline (either try) | `egress_down: true` | nothing, as before (the egress gate) | Not checked · offline 12m ago |

- **One wait a run, never one a site.** `runUptimeChecks` and the nightly
  sweep read every site first, then wait once, then ask only the pages whose
  first GET failed (`confirmHomeFailures`, `workers/ingest/src/hygiene.ts`).
  A timer costs no CPU; a scheduled Worker has 15 minutes of wall clock
  (https://developers.cloudflare.com/workers/platform/limits/); the hourly
  tick's freshness step runs beside the uptime step, so the wait holds up
  nothing else.
- **Nothing is written before the retry.** A run that dies during the wait
  leaves the hour's previous reading, which ages to Not checked; it never
  leaves a half-state the row would have to explain.
- **The nightly sweep confirms the same way**, since it files the same alert
  from the same GET.
- **Not adopted:** a recovery period (Better Stack) — the first answer
  retracts the alert, as before; and three retries (UptimeRobot) — hourly
  checks make one enough.
