# config/counters.json — the counters lane

Which of an asset's own metrics get a big-number **total** on its asset card
(the portfolio home and the Wall). This file is config, not data: the observed
values live in the store's `counter_readings` table (one current-state row per
card); this file owns *which* counters exist, their group heading and labels.

**Seed and export, not source of truth**: `pnpm config:seed` loads this
installation's copy (else this generic default) into the store's
`config_documents` table, the running OS reads and saves it there, and
`pnpm config:export` writes it to `installation/`. Until an install seeds,
every read falls back to the copy compiled into the Workers.

### What the Tower may edit here

Generated by `pnpm generate` from `scripts/config-registers.mts`, the one declaration of every register and knob; `scripts/config-docs.test.mjs` fails when this block is stale.

**Site counter cards** (`asset-counters`) — one site's counter cards. Rows live at `/assets` of `config/counters.json` (object, keyed by asset-id); edited from Add a site, then the site's Settings tab (Card totals). Rows are added and removed whole; no field inside one is set through the register.

## Semantics worth knowing

- **How often the lane reads is not in this file.** It is the counters job's
  schedule (`scripts/scheduled-jobs.mts`, changed in Settings → Data
  collection), and the Tower ages each total against that schedule's longest
  wait. The `intervalMinutes` this file used to carry is retired; a stored
  copy that still has it drops it with a `file-json-delete` changeset
  (`RETIRED_KEYS` in `scripts/config-documents.mts`).
- **`source`** is where the fast lane reads totals. Omit it and the asset
  still gets its totals from its **nightly report's own totals**, at nightly
  freshness. The one kind is `prometheus`: a text endpoint exposing
  `d1_row_count{table="<counter>"}` samples, fetched with that asset's own
  token from the ingest Worker's one `ASSET_TOKENS` map — the same endpoint
  and token as the nightly pull, because an asset authorizes one caller shape
  ([credential naming](../docs/11-integrations.md#credential-naming--the-asset_token-convention)).
  `enabled: false` pauses the fast lane; the totals stand, fed by the nightly
  report again.
- **`heading`** captions the asset's Overview group (the Wall shows metric
  names and values without it). It defaults to `All-time totals`; use a more
  truthful grain when the values are not lifetime activity (`Current catalog`).
  It is never inferred from metric names.
- **`cards[]`** render in order. `metric` is the envelope metric name — the
  join key that lets a card fall back to the nightly report's
  `metrics[metric].total` when there is no fast lane; `counter` is the
  Prometheus `table` label, required when `source.kind` is `prometheus`;
  `label` is operator copy, rendered verbatim.
- An asset with no entry gets no totals row at all. A card whose metric
  neither lane has a number for is skipped; a missing total is never drawn
  as 0.
- The fast lane is all-or-nothing per asset per run: one unreadable counter
  fails the whole asset's refresh and leaves every previous reading (value
  and timestamp) untouched — a stale total must look stale, never half-fresh.
- The lane raises no alerts. The amber age badge on the totals row, past
  twice the schedule's longest wait, is the failure signal; a nightly-fed
  total never badges because the card's header already ages that lane. A
  persistent endpoint outage is still caught within 24h by the nightly pull's
  `asset-pull-failed` alert — same endpoint, same token.
- The cards are view-only in the Tower (structural config, like the pull
  metric map); an asset's whole entry is added from its Settings tab.
