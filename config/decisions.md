# Decision register (D1–D45)

*The first config commit the Phase-0 checklist asks for
([doc 12](../docs/12-implementation-readiness.md)). Settings are store
documents, seeded from the installation folder or the defaults in this folder
and exported back to the installation folder
([doc 06](../docs/06-operations.md#reproducibility), D22); this file is the
human-readable half, [`constants.json`](constants.json) is the machine-readable
seed the workers import.*

**How to read `status`:**

- `adopted-default` — the design's default proposal is in force. **Every one is
  a proposal, not a verdict** — the operator overrides it by editing the value
  here (and its `constants.json` setting, in the Tower or with
  `pnpm config:apply`, where the value is mirrored). Nothing below is
  load-bearing on the operator having actively chosen it; the defaults let
  Phase 0 move while the operator decides.
- `deferred` — the operator is deliberately still thinking; no default is in
  force yet.
- `installation` — a decision about one installation's own sites,
  repositories, accounts or folders. It keeps its number here and is recorded
  in that installation's own decision log, `installation/decisions.md` (the
  folder `scripts/installation.mts` resolves), which a fresh clone does not
  have. The same log holds each installation's own part of a product decision
  below — which site, which folder — where this register names none (D30,
  D33).
- `pending-operator` — needs an operator input that has no sensible default
  (a calendar slot, an inventory only they can run).
- `proposed — operator to confirm` — an agent built a change that narrows a
  standing rule and wrote the reasoning down here. It is **in force in the
  code** and **not decided**: the operator confirms it or reverses it, and the
  status changes to `operator-decided` either way. Distinct from
  `adopted-default`, which is a value nobody has objected to; this is a
  direction somebody has to actually look at.
