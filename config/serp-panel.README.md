# config/serp-panel.json — the tracked-query SERP panel (S1b)

Which head terms the weekly DataForSEO lane pulls a **live Google result
page** for, per asset: the hand-picked panel [doc 08 §S1b](../docs/08-seo-geo-signals.md)
specifies, whose exact SERP neighborhood and AI-Overview citation state are
worth paying to watch, next to the broad `ranked-keywords` inventory that
answers "what do we rank for at all".

This file is config, not data. The observed result pages live in the immutable
R2 archive with one `signal_dump_runs` manifest row per asset per run
(`integration = 'dataforseo'`, `report = 'serp-panel'`); this file owns only
*which* queries exist. **Seed and export, not source of truth** (D22):
`pnpm config:seed` loads this installation's copy (else this generic default)
into the store, the running OS reads and saves it there, and
`pnpm config:export` writes it to `installation/`. Until an install seeds,
every read falls back to the copy compiled into the Workers.

### What the Tower may edit here

Generated by `pnpm config:docs -- --write` from `scripts/config-registers.mts`, the one declaration of every register and knob; `scripts/config-docs.test.mjs` fails when this block is stale.

**Sites buying a tracked panel** (`serp-panel-assets`) — one site's tracked-query panel, holding its terms. Rows live at `/assets` of `config/serp-panel.json` (object, keyed by asset-id); edited from the site's Growth tab. Rows are added and removed whole; no field inside one is set through the register.

**Tracked queries** (`serp-panel-queries`) — one tracked term, and the bet it measures. Rows live at `/assets/{asset}/queries` of `config/serp-panel.json` (array, keyed by `query`); edited from the site's Growth tab.

| Field | Label | Type | Required | Hint | Rule |
|---|---|---|---|---|---|
| `query` | Query | `string` | yes | verbatim, as a searcher types it | up to 120 characters |
| `label` | Bet | `string` | no | the bet this term counts toward | up to 60 characters; candidates suggest |

## Every collection is read (the review obligation)

A panel nobody triages is a bill with no reader. **When a collection lands,
the runner files a review bead into that asset's own tracker**
(`scripts/runner/panel-review.mjs`, reading `GET /api/serp-panel-landings` on
the ingest): labelled `panel-review`, titled *"Triage the `<YYYY-MM-DD>` serp
panel for `<asset>`"*, due seven days later, carrying `noticeos_panel_asset`
and `noticeos_panel_date`. It is filed once per asset per panel day and
re-derived from the manifest rows, so a runner that was down catches up and
one that already filed creates nothing. Adding an asset here adds a weekly
obligation, not just a weekly cost.

**The trigger is the collection, not this file.** An asset with no entry here
still buys the other report families every Monday and gets the same review
bead, scoped to the inventory pass alone. A panel adds the panel *walk* to a
review that would exist anyway, and the review is what proposes new entries.

## Semantics worth knowing

- **A query is sent verbatim, once per device**, with the collector's fixed
  dimensions: United States (`location_code: 2840`), English, phone and
  desktop, with the asynchronous AI Overview requested. An entry is a string
  or `{ "query", "label" }`, in any mix.
- **`label` is the bet the query measures** — the grouping a readout needs to
  answer "which bet is working". It is optional, belongs to the term (both
  device readings carry it), and is **never sent to DataForSEO**: the request
  body carries only fields the provider documents, and the label rides in our
  own archive envelope. **It is stored with the observation, not looked up**,
  so renaming a cluster relabels the collections that follow and leaves every
  archived one alone, and a query labelled today has an empty `query_label`
  on every earlier row.
- **An asset with no entry is skipped silently** — no call, no manifest row,
  no attempt. Absence of a panel is not a failed collection.
- **Device is two dimensions.** An AI Overview can consume the click on one
  surface and not the other. `device` rides in the archived request body and
  comes back as a column in `dataforseo-serp-panel.csv`; the two never dedupe
  against each other and the AI Overview rule applies per device. Never sum
  or average the CSV across `device`. Rows collected before the phone was
  added read `desktop`. The executive snapshot's panel readers are still
  desktop-only, named in one place (`PANEL_SNAPSHOT_DEVICE`).
- **The panel reads the top 20 results.** An asset at position 30 records no
  rank — "not inside the tracked depth", never "not ranking".
- **A missing AI Overview and an unreadable one are different facts.** When
  the overview fails to load the archive says *unknown*; only a cleanly parsed
  page with no overview says *no*. The CSV keeps that as empty-vs-`false`, and
  the query decisions treat unknown like an untracked query.
- **Cost rides the existing gate.** Each query is one metered call per device
  (`SERP_PANEL_CALL_USD`, about $0.004). The collector reserves the same
  per-report amount (`MAX_REPORT_COST_USD`, $0.25) as every other family and
  fails closed under the portfolio `monthly_caps.data_usd` cap; both devices'
  calls land on one manifest row, so the spend meter shows the real weekly
  bill. The money facts live in `packages/contract/src/dataforseo.ts` so the
  Growth tab and the collector price a term identically;
  `workers/ingest/src/dataforseo-dumps.ts` owns the enforcement.
- Editing the panel changes what the asset is *measured on*. Record the
  reason a term came or went where the decision lives, not here.

## Validation (a bad panel is a loud error, not a quiet one)

Each rule fails that **one asset's** panel for the run with a
`config_invalid` manifest row; every other asset still collects.

- **≤ 31 queries, and that number is derived, not chosen**: the biggest legal
  panel is whatever the $0.25 reserve buys (31 × 2 devices × ~$0.004). Adding
  a device halves the ceiling; raising it means raising the reserve, a
  decision about money. A panel past the ceiling is a config error, not a
  silently trimmed list; the Growth tab refuses the 32nd term in the form too.
- **No empty `queries` array, no blank strings.** An empty panel is a mistake
  worth seeing.
- **No duplicates** (case-insensitive, trimmed): one SERP billed twice.
- **A `label`, if present, is non-blank.** Omitting the field is "no label".
- **One cluster, one spelling.** Grouping is an exact match on the stored
  label, so "Item head" and "Item Head" would be two bets in the readout and
  one in the operator's head. The Growth tab and `pnpm config:apply` both
  refuse a label that differs from an existing one only in case
  (`clusterSpellingRefusal`, declared on the register as `clusterField`); the
  Bet column offers existing bets as a picker, not an allowlist.

## Where it is edited

The asset's Growth tab (`/assets/<id>/growth`), under the tracked-panel board
that reads the same panel back: a term is added, relabelled and removed one
changeset at a time, each with Undo. This file is off `ALLOWED_FILES`, so no
`file-json-set` reaches an undeclared key.

- **The first term files the entry; the last one out takes it away.** A JSON
  pointer never creates structure, so the first Add writes the whole entry;
  removing the last term removes the entry rather than leaving `queries: []`,
  which the validation above refuses.
- **The add-asset wizard writes nothing here.** A panel is a weekly bill plus
  a weekly review obligation, so the entry appears the first time an operator
  deliberately buys one.
- **The spend is stated where it is decided**: the tab prints the panel's
  weekly bill and its size against the ceiling above the Add control, and
  names the one guard that exists, `monthly_caps.data_usd` on `/settings`.
- **The asset page's Delete removes the entry with the asset.**

## Seeds

A fresh clone tracks no terms: `assets` is empty until an operator buys a
site's first panel.
