# `entities.json` — which legal entity owns which assets

An asset's owning entity is a **portfolio** fact: it decides which accounts the
money is reported under, whose paperwork covers it, and —
the moment there is more than one — how the ledger has to be split. It is not
a fact about any one data source, so it has exactly one representation: the
`assets` list on that entity's row here. Absence is *nobody has said yet*,
never *nobody owns it*.

**Seed and export, not source of truth**: `pnpm config:seed` loads this
installation's copy (else this generic default) into the store's
`config_documents` table, the running OS reads and saves it there, and
`pnpm config:export` writes it to `installation/`. Until an install seeds,
every read falls back to the copy compiled into the Workers.

### What the Tower may edit here

Generated by `pnpm generate` from `scripts/config-registers.mts`, the one declaration of every register and knob; `scripts/config-docs.test.mjs` fails when this block is stale.

**Entities** (`entities`) — one legal entity, and the sites it owns. Rows live at `/entities` of `config/entities.json` (array, keyed by `slug`); edited from /settings.

| Field | Label | Type | Required | Hint | Rule |
|---|---|---|---|---|---|
| `slug` | Id | `string` | yes | lowercase-with-dashes: acme-holdings | up to 40 characters; matches `^[a-z0-9]+(?:-[a-z0-9]+)*$`; fixed once written |
| `name` | Name | `string` | yes | as on its paperwork | up to 80 characters |
| `form` | Legal form | `string` | no | as the paperwork spells it: LLC, Ltd, sole proprietor | up to 40 characters |
| `jurisdiction` | Registered in | `string` | no | where it is registered: US-DE, Poland | up to 40 characters |
| `assets` | Sites | `string-list` | no | the site ids this entity owns | — |

## Semantics worth knowing

- **`slug` is never renamed**: every record already written names it, so a
  rename re-labels history. A change of *name* is the `name` field; a
  genuinely different legal person is a new row the assets move to.
- **`form` and `jurisdiction` are optional** because an entity that has none
  yet is a real state, and inventing one would be a claim about a filing
  nobody made. **`assets` is optional** for the same reason: an entity that
  owns nothing yet, or whose last asset moved away (`[]`), is a real state.
- **An asset belongs to at most one entity.** No field of one row can see
  another, so the surfaces that write it enforce it: `/settings` refuses an
  asset another entity already claims, and moving one from the asset's own
  page is a single change that takes it off the old list and puts it on the
  new one.
- **An empty file is the honest starting state.** A seeded row would be a
  claim about paperwork nobody has filed.

An installation seeded while the file still carried a top-level `purpose`
string drops it with one guarded `file-json-delete` of `/purpose`
(`RETIRED_KEYS` in `scripts/config-documents.mts`), applied with
`pnpm config:apply`.

## Where it is edited

**`/settings` → *Ownership*** owns the list: add an entity, correct its name,
form or jurisdiction, remove one. The table, the Add form and every refusal
come from the declaration, and the write lane validates the same rules again.
**An asset's own Settings tab → *Identity*** owns the other direction: a
picker over the entities declared here, which moves that one asset between
their `assets` lists in a single change, with Undo.

**Deleting an asset takes its id off whichever list holds it**, in the same
changeset as the register entries that go with it; the row and every other
asset it owns are untouched, because an entity is a legal person and outlives
the assets it owns.

Outside the Tower, `pnpm config:apply` makes the same store write; the file in
the installation folder is its export, not the place to change it.

## After adding this file to a checkout

`pnpm config:seed` skips every file the store already holds and loads the ones
it does not, so an install that has already seeded needs one more run:

```sh
pnpm config:seed --file config/entities.json
```
