# config/beads.json — the task hub's asset ↔ prefix ↔ database map

Beads supplies NoticeOS's common model for internal and external work; Dolt is
its central task authority. One Dolt SQL server — the
**hub** — holds every project's tasks ([Compose profile](../db/dolt/host/README.md);
an existing installation may keep a host-managed server,
[legacy profile](dolt-server.README.md)). Every repo is a **spoke**: a `bd`
client in server mode holding no database of its own, only connection
settings. This file maps the three names one project answers to — its
**asset id**, its **bead prefix** and its **database** on the hub. Start with
[Connect a task project](../docs/guides/connect-a-task-project.md) for the complete path.

`config/beads.json` is the product default (the local hub, no projects) and
`installation/beads.json` this installation's export. Settings, local
task actions, polling and task filers read the saved document; the runner does
not fall back to an export when the store is absent. Local checkout links live
separately in [`task-host.json`](task-host.README.md); deployed responses omit
host fields.

Tasks are **operator/agent coordination state, not signals.** Nothing here
enters the pulse envelope ([doc 02](../docs/02-signal-contract.md)); the hub is
a second store beside the ledger, never inside it. A bead is what someone
intends to do; a pulse is what an asset observed.

**Task projects** (`task-hub-spokes`) — one task project per site. Rows live at `/spokes` of `config/beads.json` (array, keyed by `asset`); edited from /settings.

| Field | Label | Type | Required | Hint | Rule |
|---|---|---|---|---|---|
| `asset` | Site | `asset-id` | yes | the site this project belongs to | — |
| `prefix` | Task prefix | `string` | yes | 2–8 lowercase letters, e.g. demo | up to 8 characters; matches `^[a-z]{2,8}$` |
| `database` | Database | `string` | yes | start with a lowercase letter; use lowercase letters, digits or underscores | up to 32 characters; matches `^[a-z][a-z0-9_]*$`; defaults to `prefix` |
| `repo` | Repository | `string` | no | legacy checkout metadata; local repository access is configured on the host | up to 200 characters; fixed once written |

## Why it exists

Beads' default is an embedded Dolt engine per repo: one writer at a time and
no way to ask "what is in flight across the portfolio?" Server mode makes
concurrent writers safe, and once the databases are pooled something has to
record which belongs to which asset, because the hub only knows database names
and `bd` only knows prefixes. The runner does **not** host the hub — it only
health-checks and backs it up — so tasks stay available while the app is
stopped.

## Field semantics

- **`hub`** — where the server listens and the user `bd` connects as. New
  installations name the stack's `dolt` on port 3306 as `noticeos`, with an
  installation-local credentials file; a legacy host keeps its own.
  `hub.dataDir` is legacy host metadata; Compose storage is the profile's
  `dolt-data` volume, never committed.
- **`asset`** — the join key, verbatim from `noticeos.assets`. A value that
  does not match a saved asset is a bug, not a new asset.
- **`prefix`** — visible in every bead id (`sh-1w2`) an agent ever quotes;
  renaming it rewrites every id in that database, and two projects sharing one
  make every id ambiguous.
- **`database`** — equal to the prefix by default; `bd` derives it unless
  `--database` overrides it. Two projects sharing a database merge two
  backlogs. The task-map lane reconciles the declared databases against the
  hub's `SHOW DATABASES` and files a `human` bead for a missing one.
- **`repo`** — legacy metadata kept for document history and guarded Undo,
  never used for execution. Checkout paths belong to `task-host.json`.

Local execution requires asset, prefix and database to match the host link
exactly; a mismatched link leaves that project unavailable while others run.

## Where the map is edited

**Settings → Task projects** (`/settings/task-projects`) adds, edits and removes a
project with the same guarded write, Undo toast and refusals as every other
register on that page; a duplicate prefix or database is refused before the
request is made, and the asset column offers the assets no project has
claimed. Fresh setup creates the System's project before any user site exists.
Hosted builds show the map read-only and omit host paths and connection
details. Adding a row does not provision a database or checkout: the local
page supplies the setup steps left for the host. Editing an export has no
runtime effect until a guarded `pnpm config:apply`.

## How a new project joins

Add its entry in **Settings → Task projects**, then run the setup checklist's
command in the project checkout while the hub is running. For a Compose
installation it calls `scripts/dolt-project.mjs`, which supplies the
installation's password only to the initialization process (the pinned Beads
CLI does not read its credentials file during `init`). The legacy managed
host uses:

```
bd init --server --external --server-host 127.0.0.1 --server-port 3308 \
  --server-user root --prefix <PREFIX> --non-interactive --skip-agents --skip-hooks
```

For later manual `bd` commands on a Compose installation, set
`BEADS_CREDENTIALS_FILE` to the installation folder's `state/dolt/credentials`.

`--external` keeps the hub-and-spoke shape honest: without it `bd` silently
starts its own Dolt server when the configured one is unreachable, and the
project stops sharing the hub while appearing to work. `--skip-agents` keeps
`bd` from writing `AGENTS.md`, `CLAUDE.md`, `.claude/` and `.codex/`
scaffolding into the repo; `--skip-hooks` keeps it from repointing
`core.hooksPath` at `.beads/hooks`, which silently disables the repo's own
hooks.

**After a legacy `bd init`, fix `.beads/config.yaml`** (the Compose helper
applies this spoke standard itself):

1. **No `sync.remote`, ever.** `bd init` writes one pointing at the repo's git
   remote; delete it. With it present, `bd dolt push/pull` has a live target
   and would fork a private, diverging issue store beside the hub.
2. **`no-git-ops: true`** — silences the hook's "no Dolt remote configured …
   repair: `bd dolt push`" advice (that repair is the fork above) and keeps
   `bd` from running its own git operations.
3. **`import.auto: false`** — `import.auto` defaults to true: on every git
   pull/merge/checkout `bd` could upsert-import a stale JSONL export into the
   shared hub. The hub is authoritative; automatic imports are always wrong.

The three land **together**: removing `sync.remote` without the key pair
silently arms the reimport hazard.

**Link the checkout on this host** by adding a matching asset, prefix,
database and repository path to `installation/task-host.json`
([field contract](task-host.README.md)). This explicit host step grants access
to the checkout; a database setting cannot select an arbitrary directory.

### Moving a maintainer checkout

Moving source to another checkout does not create a new task project: the
existing database, prefix and project identity remain authoritative. Public
contributors follow [CONTRIBUTING.md](../CONTRIBUTING.md) without private hub
access.

1. Establish the exact existing service and database from the previous
   checkout's connection metadata and protected host-client declaration, and
   obtain the operator's authorization for the new checkout's access.
2. Create the new checkout's private `.beads/` and copy only the existing
   `metadata.json`. Set `no-git-ops: true`, `import.auto: false` and
   `export.auto: false` in its `config.yaml`, with the same connection and
   prefix; keep `sync.remote` absent. Do not run `bd init`, import a JSONL
   export, copy a database, or create another project.
3. For the bundled Docker adapter, add the exact checkout path to the
   protected host plan's `spokes` list and create its regular
   `.beads.gate.lock` file. Preserve the accepted image, network, client
   profile, credentials and other allowed paths; do not restart the hub.
4. From the new checkout, run `bd ready`, `bd list` and `bd show` for a known
   task; claim with the actual agent's `--actor`; verify another spoke still
   works.

The host client's allowed checkout list and the application's
[`task-host.json`](task-host.README.md) inventory are distinct access
boundaries: changing the client list grants agent CLI access only.

### The spoke stanza

Every spoke's `CLAUDE.md` (and its `AGENTS.md`, where it has one) carries the
same stanza, byte-identical, under its own repo-specific intro. It is a pointer,
not the rules: the rules come from the `noticeos` MCP server's `get_task_guide`
tool and its instructions, so they reach every agent without a copy to keep in
step. The canonical stanza lives here between the markers;
`scripts/spoke-stanza.test.mjs` fails when a spoke's copy drifts. Change it here
first, then re-stamp the spokes.

- Tasks and site data come from the `noticeos` MCP server. Call `get_task_guide` before task work: it returns the workflow and the rules for filing, claiming and closing a task.
- Never run `bd`, `bv` or `br` in this repository: the MCP tools are the task interface.
- Work only a person can do carries the `human` label; a step that must wait for approval uses `request_human_approval`.

## Semantics worth knowing

- **The spoke's `.beads/` holds no issues** — connection settings plus a
  `README` and a `.gitignore`. Deleting it loses nothing but the pointer;
  deleting the hub's data directory loses every task in the portfolio.
- **The hub must be up before `bd` is useful.** With the service stopped,
  `bd` fails to connect rather than falling back, per `--external`. Recover
  the declared service with the
  [Compose procedure](../db/dolt/host/README.md#backup-and-recovery); with
  `NOTICEOS_DOLT_HOME` selected, a missing profile is a recovery condition,
  never permission to start the old native hub. Stopping the app does not take
  the hub down.
- **Prefix ≠ asset id, and both are load-bearing.** This file is the only
  place the two are tied together.
- **`interactions.jsonl` is never committed.** It is `bd`'s per-machine
  append-only interaction audit; every spoke's `.beads/.gitignore` covers it.
  If a tree shows it modified or untracked, re-apply
  `git rm --cached .beads/interactions.jsonl` plus the gitignore line.
- **`br` (beads_rust) must never be run in a spoke.** It is a separate
  SQLite + JSONL implementation with no Dolt backend: `br create` would
  scaffold a private, divergent store inside `.beads/`. `bv` is retired.
  **`bd` is the only task CLI.**

## The Tower's task lane — the operator's hands, not an agent's

`bd` is the only write path an agent uses: an agent claims and closes work in
the repo where the work happens, because that is where it has the context to be
honest about what it did. The operator also has a UI. The hub is a Dolt server
on the installation's network that a Worker cannot reach, but the Tower's dev
server in the app container can: a local lane (`apps/tower/vite/task-lane.ts`, serving
`/api/tasks/*` and `/api/gates/*`) runs `bd` for the operator inside the
checkout `task-host.json` links to each saved project, the same projects the
poller reads. Three guards, all load-bearing:

- **Same origin** (`apps/tower/vite/lane.ts`, the guard the config lane uses),
  for reads too, since every path spawns a process. The LAN Tower has no
  authentication, so what must be impossible is another site steering the
  browser into a write here.
- **An allowlist of twelve verbs** (`ALLOWED_VERBS`), checked before anything
  is spawned: reads `list`, `ready`, `show`, `comments`, `epic status`; writes
  `create`, `update` (including `--claim` and `--defer`), `close -r`,
  `comments add`, `human respond`, `human dismiss`, `gate resolve`. Anything
  else (`delete`, `sql`, `dolt`, `import`, `export`, `federation`, `backup`,
  `restore`, `config`, `hooks`, `compact`, …) is refused with the verb named.
- **`--actor` on every write**, the checkout's own `git user.name`, so the
  hub's audit trail keeps saying who touched what.

`bd`'s stderr comes back verbatim in `detail`; a non-zero exit is a
`502 bd_failed`, never a silent nothing. A deployed Tower compiles the lane out
(`apply: "serve"`): its Worker answers `GET /api/tasks/capabilities` with
`{live: false}` and every other task path with `501 read_only_deployment`
(`apps/tower/worker/tasks-route.ts`), and keeps the read-only snapshot board.
The lane's File button replaces the pasted `bd create` command, not the
judgment.

## Conventions

The hub is the portfolio's **only** register of open work. The process rules
— file a bead, claim before building, verify, close with evidence, the `human`
label and gates — are written once, in
[AGENTS.md](../AGENTS.md#open-work-lives-in-the-task-hub), and how to write a
task is `TASK_QUALITY` in
[`scripts/hosted-task-mcp.mts`](../scripts/hosted-task-mcp.mts), which the task
tools send to every connected agent. What belongs here is the filing grammar
`bd` needs.

- **Epics.** Related work groups under a `-t epic` bead carrying an
  operator-readable theme title and a paragraph on why the members belong
  together; create one when three or more beads share a theme. Membership is
  the parent link (`bd create --parent <epic>`, `bd update <id> --parent
  <epic>`), which `bd epic status` and `bd epic close-eligible` read. An epic
  is a container; it holds no work of its own.
- **Dependencies.** `bd dep <blocker> --blocks <blocked>`, or equivalently
  `bd dep add <blocked> <blocker>` — the two forms take their arguments in
  opposite orders. Only real blocking edges; for "related, neither blocks",
  `bd dep relate`.
- **Defer.** Work blocked on time rather than effort: `bd update <id> --defer
  <+4w | YYYY-MM-DD>` (also `+6h`, `tomorrow`, `next monday`; an empty string
  clears it). A deferred bead leaves `bd ready` until its date and stays in
  `bd list`; the description says why.
- **Description shape.** Plain labelled lines — `WHAT:` / `WHY:` / `WHERE:`,
  plus `ORDER:` or `CONSTRAINT:` where one applies — in unwrapped paragraphs,
  because `bd show` re-wraps and renders headings as literal `##`. One
  exception: `bd lint`'s bug template requires a literal
  `## Steps to Reproduce`. `--acceptance` is a first-class field.
- **Gates.** `bd gate create --type human` holds a bead out of `bd ready`
  until `bd gate resolve`. Other types: `timer`, `gh:run` / `gh:pr` and `bead`
  (a cross-project bead as `<project>:<id>`); verify a type against
  `bd gate --help` before relying on it.
- **Observations are not commitments.** The analyzer never writes to the
  register: insight cards and query decisions are regenerated from archives on
  every run; a bead exists only when a person files one. A finding renders its
  bead once one exists, joined by `noticeos_key`.

### Handoff metadata

Beads filed from the Tower's handoff surfaces carry a fixed metadata grammar,
so a finding can be traced back to the rule that produced it: `noticeos_source`
(always `noticeos-handoff`), `noticeos_asset`, `noticeos_kind`, `noticeos_rule`,
`noticeos_key` — plus labels `asset:<id>`, `rule:<slug>`, `key:<slug>`. The
emitter is
[`apps/tower/src/lib/task-handoff.ts`](../apps/tower/src/lib/task-handoff.ts),
and `bd list --metadata-field 'noticeos_key=<exact>'` finds a bead by its
origin. Filing the same class of work by hand? Use the same keys.

Beads filed before the NoticeOS rename carry the same grammar under the old
names — `reindex_source`, `reindex_asset`, `reindex_kind`, `reindex_rule`,
`reindex_key` and the `reindex-handoff` label — and stay valid forever: every
reader takes either name
([`packages/contract/src/task-metadata.mts`](../packages/contract/src/task-metadata.mts)).
Never rewrite an old bead's metadata to the new names.

**Who did the work.** `bd` records the assignee a claim sets but not who
closed a task, how the close ended or the model a filer named, so NoticeOS
writes eight more keys itself, and metadata sent with a new task may not
include them (nor the two keys of [What a task is worth](#what-a-task-is-worth),
which arrive in fields of their own): `noticeos_filed_by` and `noticeos_filed_model` (who filed the
task through the task tools and the model it named, written in the create
itself), `noticeos_claimed_model` (the model an agent named when it claimed
the task), and, written in one update just after a close,
`noticeos_closed_by`, `noticeos_closed_model`, `noticeos_closed_at`,
`noticeos_resolution` and `noticeos_duplicate_of`. The closer applies only to
the close at `noticeos_closed_at`; a task reopened and closed again without a
new record shows its close and no closer. A task filed with `bd` directly, or
by one of the runner's filers, carries no `noticeos_filed_by` and names no
filer.

`noticeos_resolution` is one of `done`, `wont-do`, `duplicate`,
`cant-reproduce` and `already-handled`
([`packages/contract/src/task-resolution.mts`](../packages/contract/src/task-resolution.mts)),
shown as Done, Won't do, Duplicate, Can't reproduce and Already handled.
Every close the task tools or the Tower make writes it, `done` when the close
names none; a dismissed ask writes `wont-do`, or the other resolution the
person picked, and is never `done`.
`noticeos_duplicate_of` is written with `duplicate` only and names the other
task, which must be in the same project and is linked to the closed one as
`related`. A task with no `noticeos_resolution`, or one recorded for an
earlier close, reads as `done`. The close reason stays the text the closer
gave. Only a `done` close counts as work done on the Agents page.

Two more server-written keys hold a person's pick, as JSON objects rather
than text. `noticeos_choices` is the set of options a task offers, written
from the `choices` an agent passes to `create_task`, `create_tasks` or
`update_task` once they pass the rules in
[`packages/contract/src/task-choices.mts`](../packages/contract/src/task-choices.mts):
`{ question, options: [{ key, label, detail?, recommended? }] }`, two to six
options keyed `a` to `f` in the order shown, exactly one with
`recommended: true`. `noticeos_choice` is the pick, written once by the
choose operation, or by `reconcile_task` after verifying an existing owner answer and its proposal:
`{ option, label, by, at, note? }`, where `label` is the option's label when
it was chosen and `by` is the person. Once `noticeos_choice` is present,
`update_task` refuses to change `noticeos_choices`.

`noticeos_maintenance` records the last evidence-backed task disposition,
its actor, source, exact proposal and scope. Task history retains earlier
records. A retired gate records no permission; its unfinished action remains
blocked, or retains an equivalent open approval when it is a duplicate.
A linked-conversation answer requires a trusted source adapter. Without that
adapter, the recorded answer stays available and the operation fails closed;
the owner does not need to answer again. A task-comment answer must match its
human owner and the proposal at the comment's timestamp.

**Four kinds, and what each one's key is.** `noticeos_kind` names the surface
that raised the work, and `noticeos_key` is the join back to the exact row:

| `noticeos_kind` | Surface | `noticeos_key` | `noticeos_rule` |
|---|---|---|---|
| `finding` | the asset page's executive findings | the finding's card key (`ExecutiveInsight.key`) | the same card key |
| `query` | the asset page's query decisions | the normalized query, byte-exact | the decision kind (`recover`, `near-win`, …) |
| `page` | the asset page's page decisions | the absolute page **URL**, never its path — two assets can share `/recipes` | the page decision kind |
| `alert` | `/alerts` and the desk's attention table | `flags.id` as a string | the flag's `rule_id` |

`alert` is the one key that is a database id rather than a string the operator
would recognize, deliberately: one rule fires many times on one asset, and only
the flag id names the firing the operator was looking at.

Every one of those surfaces carries a **File task** button beside its Copy
Markdown: it opens a composer on exactly the bead the copied `bd create`
describes (`taskHandoffPrefill`) and files it through the task lane in the
asset's own spoke. Copy Markdown stays for agents and is the only path in a
deployed build.

The list of kinds is **stated in five places that ship separately** — the
emitter's `TaskHandoffKind`, the contract's `BEADS_HANDOFF_KINDS`
(`packages/contract/src/task-snapshot.mts`, which the poller and the ingest
validator both import), the Tower reader's `readHandoff`
(`apps/tower/worker/beads-snapshot.ts`), the shared type `HandoffKind`
(`apps/tower/shared/asset-detail.ts`), and **the table above** — so widen all
five together; `scripts/handoff-kinds.test.mjs` reads every one and names the
odd one out. At runtime an unknown kind costs its own
row, the rest of the project stores, and the Worker logs one
`beads_handoff_kind_unknown` line per snapshot.

The grammar has a reader as well as an emitter: the runner's poller lists
handoff beads by label against every spoke and carries `noticeos_key` /
`noticeos_kind` / `noticeos_asset` into the beads snapshot, so the Tower
renders a finding's bead — id and open/closed — on the card that raised it.
The label and those three fields are therefore a contract with a rendered
surface; the key must stay byte-exact in metadata (the `key:` label is a lossy
slug); and a bead filed in the wrong repo is dropped rather than shown, since
finding keys are rule ids every property shares.

### What a task is worth

Two keys record why a task is worth doing and what kind of change it makes.
Whoever files or edits the task writes them: an agent through the task tools'
`card` and `change_class` arguments (`create_task`, `create_tasks`,
`update_task`), the operator through the Tower's task lane and the hosted
Tasks API, whose fields are `card` and `changeClass`. Each is checked in its
own field before anything is written. `null` on an update removes the key.
One update either sets these keys or removes them, never both, because
`bd update` takes either one merged `--metadata` object or `--unset-metadata`
keys in a single command.

`noticeos_card` is a JSON object, checked by `taskCardProblem` in
[`packages/contract/src/task-card.mts`](../packages/contract/src/task-card.mts):

| Field | Value |
|---|---|
| `valuePerMonth` | the predicted change in ledger value, USD a month, −1,000,000 to 1,000,000; a loss the task avoids is positive |
| `likelihood` | the probability that the change pays off, 0.01 to 0.99 |
| `reviewMinutes` | the operator's minutes to review and decide, 0 to 100,000 |
| `buildMinutes` | optional: the agent's or builder's minutes, 0 to 1,000,000, shown beside the score and not priced |
| `daysToSignal` | whole days until the ledger shows whether the change worked, 1 to 730 |
| `measurability` | `cohort`, `holdout` or `unmeasured` |
| `revenueFamily` | optional: `ads`, `affiliate`, `subs` or `licensing` |
| `durability` | optional: the forecastability multiplier F, 0.5 to 1.2; 1 when absent |
| `kill` | optional: `{ state, date }`, the state that, still true on `date` (`YYYY-MM-DD`), parks the task |
| `note` | optional: one line of at most 600 characters, the reason the money moves |
| `by`, `at` | who recorded the card, and when, as an ISO 8601 time |

The server writes `by` and `at` on every write of a card, as the admitted
actor (the same value as `noticeos_filed_by`) and the time of the write, and
replaces any `by` or `at` the caller sent. The task lane writes the checkout's
`git user.name` and its own clock. A card's `kill.date` is also the task's due
date: the same create or update passes it to `bd` as `--due`. Removing a card
leaves the due date unchanged.

`noticeos_change_class` is one of `content-data`, `copy`, `template`,
`feature` and `infra`
([`packages/contract/src/task-change-class.mts`](../packages/contract/src/task-change-class.mts)),
shown as Content data, Copy, Template, Feature and Infrastructure. The
autonomy ladder ([doc 05](../docs/05-execution-and-accountability.md)) and
the likelihood priors ([doc 04](../docs/04-decision-policy.md)) are kept per
class.

The Tower ranks tasks by their cards with policy v1.0, the scoring function
of [doc 04](../docs/04-decision-policy.md):
`(likelihood × valuePerMonth × durability) / review cost / max(weeks to signal, 2)`,
where the review cost is `reviewMinutes` at the installation's
`operator_rate_usd_per_min`. A task without a card is listed and not ranked.
Every reader goes through `readTaskCard` and `readTaskChangeClass`, which read
a value that fails the rules as no card and no class.

## Seeds

A fresh clone declares no projects: `config/beads.json` carries the hub
connection and an empty `spokes` list. An installation's own projects are its
saved task projects and its host links ([`task-host.json`](task-host.README.md)).
