# config/beads.json — which Ntasks project holds each asset's tasks

Ntasks holds the installation's tasks
([Keep tasks in Ntasks](../docs/guides/keep-tasks-in-ntasks.md)). This file
maps the two names one task project answers to: its **asset id** and its
**task prefix**. Each row maps its asset to the Ntasks project with the same
prefix. Start with
[Connect a task project](../docs/guides/connect-a-task-project.md) for the
complete path.

`config/beads.json` is the product default (no projects) and
`installation/beads.json` this installation's export. Settings, the **Tasks**
pages, the runner's task snapshot and its review filers read the saved
document; the runner does not fall back to an export when the store is absent.
Each row keeps a `database` from when tasks lived in a Dolt server; Ntasks
does not use it.

Tasks are **operator/agent coordination state, not signals.** Nothing here
enters the pulse envelope ([doc 02](../docs/02-signal-contract.md)); Ntasks is
a second store beside the ledger, never inside it. A task is what someone
intends to do; a pulse is what an asset observed.

## Why it exists

Ntasks knows a project by its prefix, and NoticeOS knows an asset by its asset
id. This map is the one place the two are tied together, so a finding, an
asset's page and the task snapshot name the right project.

## Field semantics

- **`asset`** — the join key, verbatim from `noticeos.assets`. A value that
  does not match a saved asset is a bug, not a new asset.
- **`prefix`** — visible in every task id (`sh-1w2`) an agent ever quotes, and
  the prefix of the Ntasks project that holds the asset's tasks. Two projects
  sharing one make every id ambiguous.
- **`database`** — takes the prefix by default; Ntasks does not use it.
- **`repo`** — legacy metadata kept for document history and guarded Undo,
  never used for execution.
- **`hub`** — not used.

## Where the map is edited

**Settings → Task projects** (`/settings/task-projects`) adds, edits and removes a
project with the same guarded write, Undo toast and refusals as every other
register on that page; a duplicate prefix or database is refused before the
request is made, and the asset column offers the assets no project has
claimed. Fresh setup creates the System's project before any user asset exists.
Hosted builds show the map read-only. Adding a row does not make the project
in Ntasks. Editing an export has no runtime effect until a guarded
`pnpm config:apply`.

## How a project connects

Make the project in Ntasks with the asset's prefix, give the installation a
service credential that reaches it, and save the asset and prefix in
**Settings → Task projects**
([Connect a task project](../docs/guides/connect-a-task-project.md)). No
checkout is required.

### Moving a maintainer checkout

Moving source does not change the task connection: the project stays in Ntasks
under its prefix. No task files need to be copied into the new checkout.
`project:prepare` supplies an optional instruction pointer only. Public
contributors follow [CONTRIBUTING.md](../CONTRIBUTING.md) without access to the
maintainers' Ntasks.

### The spoke stanza

Every spoke's `CLAUDE.md` (and its `AGENTS.md`, where it has one) carries the
same stanza, byte-identical, under its own repo-specific intro. The stanza
points to the rules and does not copy them: the `noticeos` MCP server's
`get_task_guide` returns the installation's task rules and which MCP server
serves its task tools, and when that is Ntasks's endpoint, the `ntasks` MCP
server's `get_task_guide` returns the workflow and the rules for writing a
task, so a rule change reaches every agent with no copy to update. A
spoke holds no task files: no `.beads/` directory, no `.beads.gate.lock` and no
`.beads` lines in its `.gitignore`. The canonical stanza is the text between
the markers below. `scripts/spoke-stanza.test.mjs` fails when a checked-out
spoke's copy differs from it or the spoke still holds a task file. Change the
stanza here first, then re-stamp the spokes.

<!-- spoke-stanza:begin -->
- Asset data comes from the `noticeos` MCP server. Before task work, call its `get_task_guide`: it returns this installation's task rules and which MCP server serves its task tools. When it directs you to Ntasks's MCP endpoint, also call `get_task_guide` on the `ntasks` MCP server and use its task tools. When it says no task service is connected, stop task work and ask the owner to connect one in the Tower. Otherwise use the `noticeos` task tools.
- Never run `bd`, `bv` or `br`: the MCP task tools are the task interface. If the server the guide names is missing from your session, ask the owner to connect it.
- Work only a person can do carries the `human` label; a step that must wait for approval uses `request_human_approval`.

## Semantics worth knowing

- **Prefix ≠ asset id, and both are load-bearing.** This file is the only
  place the two are tied together.
- **No task CLI runs.** Agents use Ntasks's MCP task tools, which the stanza
  above names. `bd`, `br` and `bv` are retired.

## The Tower's task routes

On an installation the Tower's dev server serves `/api/tasks/*` and
`/api/gates/*` (`apps/tower/vite/task-service-lane.ts`). It sends each read and
change to Ntasks through the ingest Worker with the installation's service
credential, and Ntasks records the change as
`service:<credential name>/tower`. A person's decisions go from their browser
to Ntasks with their own sign-in
([Decisions and approvals](../docs/guides/keep-tasks-in-ntasks.md#decisions-and-approvals)).
A deployed Tower compiles these routes out (`apply: "serve"`): its Worker
answers `GET /api/tasks/capabilities` with `{live: false}` and every other task
path with `501 read_only_deployment` (`apps/tower/worker/tasks-route.ts`).

## Conventions

Ntasks is the portfolio's **only** register of open work. The process rules
— file a task, claim before building, verify, close with evidence, the `human`
label and approvals — are written once, in
[AGENTS.md](../AGENTS.md#open-work-lives-in-ntasks), and how to write a task is
in Ntasks's `get_task_guide`, which its MCP server sends to every connected
agent.

**Observations are not commitments.** The analyzer never writes to the
register: insight cards and query decisions are regenerated from archives on
every run; a task exists only when a person files one. A finding renders its
task once one exists, joined by `noticeos_key`.

### Handoff metadata

Tasks filed from the Tower's handoff surfaces carry a fixed metadata grammar,
so a finding can be traced back to the rule that produced it: `noticeos_source`
(always `noticeos-handoff`), `noticeos_asset`, `noticeos_kind`, `noticeos_rule`,
`noticeos_key` — plus labels `asset:<id>`, `rule:<slug>`, `key:<slug>`. The
emitter is
[`apps/tower/src/lib/task-handoff.ts`](../apps/tower/src/lib/task-handoff.ts),
and Ntasks's `create_task` takes exactly these five keys as its `metadata`.
Filing the same class of work by hand? Use the same keys.

Tasks filed before the NoticeOS rename carry the same grammar under the old
names — `reindex_source`, `reindex_asset`, `reindex_kind`, `reindex_rule`,
`reindex_key` and the `reindex-handoff` label — and stay valid forever: every
reader takes either name
([`packages/contract/src/task-metadata.mts`](../packages/contract/src/task-metadata.mts)).
Never rewrite an old task's metadata to the new names.

**Who did the work.** Ntasks records on each task who claimed and closed it,
the model each named, how the close ended and the task it duplicates. The
Tower reads them in the shape of these metadata keys
([`scripts/task-service.mts`](../scripts/task-service.mts) `withNoticeosRecords`,
[`packages/contract/src/task-metadata.mts`](../packages/contract/src/task-metadata.mts)):
`noticeos_claimed_model`, `noticeos_closed_by`, `noticeos_closed_model`,
`noticeos_closed_at`, `noticeos_resolution` and `noticeos_duplicate_of`. A
close Ntasks imported without a closer has none of them.

`noticeos_resolution` is one of the resolutions in
[`packages/contract/src/task-resolution.mts`](../packages/contract/src/task-resolution.mts):
`done`, `wont-do`, `duplicate`, `cant-reproduce`, `already-handled` and
`no-longer-needed`, shown as Done, Won't do, Duplicate, Can't reproduce,
Already handled and No longer needed. A task with no `noticeos_resolution`
reads as `done`. Only a `done` close counts as work done on the Agents page.

A task's choices, a person's pick, an owner's answer and an evidence-backed
retirement are Ntasks's own fields; its `get_task_guide` describes them.

**Four kinds, and what each one's key is.** `noticeos_kind` names the surface
that raised the work, and `noticeos_key` is the join back to the exact row:

| `noticeos_kind` | Surface | `noticeos_key` | `noticeos_rule` |
|---|---|---|---|
| `finding` | the asset page's executive findings | the finding's card key (`ExecutiveInsight.key`) | the same card key |
| `query` | the asset page's query decisions | the normalized query, byte-exact | the decision kind (`recover`, `near-win`, …) |
| `page` | the asset page's page decisions | the absolute page **URL**, never its path — two assets can share `/recipes` | the page decision kind |
| `alert` | `/alerts` and the desk's attention table | `flags.id` as a string | the flag's `rule_id` |

`alert` is the one key that is a database id rather than a string the operator
would recognize, deliberately: one rule fires many times on one asset, and only
the flag id names the firing the operator was looking at.

Every one of those surfaces carries a **File task** button beside its Copy
Markdown: it opens a composer on the task the copied Markdown describes
(`taskHandoffPrefill`) and files it in the asset's own Ntasks project. Copy
Markdown stays for agents and is the only path in a deployed build.

The list of kinds is **stated in five places that ship separately** — the
emitter's `TaskHandoffKind`, the contract's `BEADS_HANDOFF_KINDS`
(`packages/contract/src/task-snapshot.mts`, which the poller and the ingest
validator both import), the Tower reader's `readHandoff`
(`apps/tower/worker/task-snapshot.ts`), the shared type `HandoffKind`
(`apps/tower/shared/asset-detail.ts`), and **the table above** — so widen all
five together; `scripts/handoff-kinds.test.mjs` reads every one and names the
odd one out. At runtime an unknown kind costs its own
row, the rest of the project stores, and the Worker logs one
`task_handoff_kind_unknown` line per snapshot.

The grammar has a reader as well as an emitter: the runner reads every task
carrying a handoff label from Ntasks and carries `noticeos_key` /
`noticeos_kind` / `noticeos_asset` into the task snapshot, so the Tower
renders a finding's task — id and open/closed — on the card that raised it.
The label and those three fields are therefore a contract with a rendered
surface; the key must stay byte-exact in metadata (the `key:` label is a lossy
slug); and a task filed in the wrong project is dropped rather than shown,
since finding keys are rule ids every asset shares.

### What a task is worth

Two fields record why a task is worth doing and what kind of change it makes,
and a third keeps the card a task shipped with. Agents write the first two
through Ntasks's task tools: `card` and `change_class` on `create_task`,
`create_tasks` and `update_task`. Ntasks checks each before anything is
written, records who wrote the card and when, and keeps the card a task first
closed as done with.

`noticeos_card` is a JSON object, checked by `taskCardProblem` in
[`packages/contract/src/task-card.mts`](../packages/contract/src/task-card.mts):

| Field | Value |
|---|---|
| `valuePerMonth` | the predicted change in ledger value, USD a month, −1,000,000 to 1,000,000; a loss the task avoids is positive |
| `likelihood` | the probability that the change pays off, 0.01 to 0.99 |
| `reviewMinutes` | the operator's minutes to review and decide, 0 to 100,000 |
| `buildMinutes` | optional: the agent's or builder's minutes, 0 to 1,000,000, shown beside the score and not priced |
| `daysToSignal` | whole days until the ledger shows whether the change worked, 1 to 730 |
| `measurability` | `cohort`, `holdout` or `unmeasured` |
| `revenueFamily` | optional: `ads`, `affiliate`, `subs` or `licensing` |
| `durability` | optional: the forecastability multiplier F, 0.5 to 1.2; 1 when absent |
| `kill` | optional: `{ state, date }`, the state that, still true on `date` (`YYYY-MM-DD`), parks the task |
| `note` | optional: one line of at most 600 characters, the reason the money moves |
| `by`, `at` | who recorded the card, and when, as an ISO 8601 time |

A card's `kill.date` is also the task's due date.

`noticeos_change_class` is one of `content-data`, `copy`, `template`,
`feature` and `infra`
([`packages/contract/src/task-change-class.mts`](../packages/contract/src/task-change-class.mts)),
shown as Content data, Copy, Template, Feature and Infrastructure. The
autonomy ladder ([doc 05](../docs/05-execution-and-accountability.md)) and
the likelihood priors ([doc 04](../docs/04-decision-policy.md)) are kept per
class.

`noticeos_card_shipped` is the card as it stood when the task first closed
as done: `{ card, closedAt, commit? }`. It is never edited: a reopened task
keeps it, a later close as done leaves it as it was, and Ntasks stops a change
to a shipped task's card. It holds the prediction the change is graded against
([doc 04](../docs/04-decision-policy.md)). `readTaskCardShipped` reads it, and
reads a value that fails its rules as none.

Policy v1.0, the scoring function of [doc 04](../docs/04-decision-policy.md),
scores a card as
`(likelihood × valuePerMonth × durability) / review cost / max(weeks to signal, 2)`,
where the review cost is `reviewMinutes` at the installation's
`operator_rate_usd_per_min`; no Tower page ranks tasks by it today.
Every reader goes through `readTaskCard` and `readTaskChangeClass`, which read
a value that fails the rules as no card and no class.

## Seeds

A fresh clone declares no projects: `config/beads.json` carries an empty
`spokes` list. An installation's own projects are its saved task projects.
